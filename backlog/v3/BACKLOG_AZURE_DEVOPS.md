# Backlog mestre — JL Design Tech V3

> **Estrutura Azure DevOps:** Epic = módulo, Feature = funcionalidade, User Story = tela ou operação independente. Esta organização **não cria automaticamente work items no Azure DevOps**; o CSV é uma base de preparação para importação/mapeamento de pais.

**Fonte:** 118 US existentes, preservadas sem alterar seus critérios; lacunas propostas em seção separada. **Estado inicial:** A validar — não significa que código inexiste. A conclusão exige evidência de código, teste e homologação da US.

## Regras de gestão

- **Epic:** 1 por módulo; **Feature:** funcionalidade coesa; **User Story:** resultado testável e pequeno, preferencialmente uma tela ou operação de CRUD.
- US de **criar, listar, visualizar, editar, excluir/desativar** devem ser separadas quando aplicáveis; não criar CRUD artificial para telas somente leitura, relatórios ou integrações.
- Cada US deve conter EU COMO, DESEJO, COM O OBJETIVO, protótipo quando houver tela, navegação, campos, validações, botões, regras e critérios de aceitação **por último**, sem numeração, no formato DADO/QUANDO/ENTÃO/SE/E.
- Estados sugeridos: **Proposta → A refinar → Pronta para desenvolvimento → Em desenvolvimento → Em revisão → Em teste → Homologada**; bloqueios e bugs são rastreados separadamente.
- Relação de dependência: M01–06 fornecem fluxos públicos e dados; M07–08 administram catálogo e afiliados; M09 autoriza e sincroniza fonte externa; M10 consulta e concilia pedidos; M11 depende de dados confiáveis; M12 governa acesso e auditoria.
- **Importação Azure DevOps:** colunas *External ID* e *Parent External ID* são referências auxiliares. O CSV não estabelece hierarquia automaticamente; após importar, vincular Epic → Feature → User Story via links Parent/Child no Azure DevOps. *Area Path* e *Iteration Path* vazios para não inventar configurações da organização.
- Não declarar uma US pronta só por haver model, Django Admin ou template; registrar evidência e validar cada critério.
